### OpenCV 颜色识别预览窗口（修了两个 bug）

`ugv_ws/opencv_color_lab.py` 双击即崩，逐层排查发现是**两个叠加的 bug**：

1. **首帧前 `cv2.destroyWindow` 不存在的窗口**（QT 后端直接抛 NULL guiReceiver）——
   已改为只建窗不销毁；预设色切换改用 `setTrackbarPos` 移动滑条，不再销毁重建窗口。
2. **真正杀招：窗口标题含中文**。容器内 OpenCV 是 QT 后端，中文标题下 `imshow` 能建窗
   （`WND_PROP_VISIBLE=1`）但 `createTrackbar` 按名字找窗必失败（NULL window handler），
   **改 LANG/LC_ALL 为 C.UTF-8、en_US.UTF-8 均无效**（QT 内部编解码路径问题）。
   处置：标题改 ASCII `"OpenCV Color Lab (q quit | r/g/b/y preset)"`，文件内注释说明原因。

验证：容器内实跑窗口真实出现（xwininfo 1280×700）、零报错退出；
`set_trackbarPos` 切预设色路径为 OpenCV 标准 API，无需再验。
**教训：本机（容器 QT 后端）所有 cv2 窗口标题必须 ASCII。**

## 2026-10-27 晚：会话模式再发内存冻结事故（两次重启）与修复

**事故**：16:27:59 从会话模式菜单 BENCH→ROS2 后，接连两次"运存炸"冻结死机，
16:28 与 17:20 两档启动各只活了 52min / 5min 即被强制断电重启（kern.log 当日**无任何
OOM kill 记录**，earlyoom 也零触发）。

**根因**：earlyoom 触发条件是"可用内存<10% **且** swap 空闲<10%"（AND，见其 --help）。
本机 swap 共 5.8G（zram 1.8G + swapfile 4G），永远到不了"swap 空闲<10%"那条线 →
**安全网等于不设防**；zram 压满后 CPU 被压缩线程拖死，画面定格，用户只能断电。

**修复**（菜单加固 + earlyoom 均已生效，17:47 经 pkexec 图形授权执行
`cp /tmp/earlyoom.new /etc/default/earlyoom && systemctl restart earlyoom`，
syslog 确认 `mem <= 15.00% and swap <= 100.00%`）：

1. **earlyoom 改只看内存**：`EARLYOOM_ARGS="-r 3600 -p -m 15 -s 100"`
   （-m 15：可用内存<15%≈540MB 时 SIGTERM 最大进程、<7.5% SIGKILL；-s 100 让 swap
   条件恒真； -p 提升 earlyoom 自身优先级防它自己卡死）。
2. **`~/ugv_mode_menu.sh` 加固**：新增 `mem_avail_mb`/`mem_guard`——可用内存<600MB 时
   启动任何 ROS2 实验需输 yes 确认；菜单头部常显内存；选项2/4（导航/slam_nav）不再
   硬编码 `use_rviz:=true`，改询问、**默认不开**（省 ~500MB，笔记本可远程开 RViz）；
   选项1/2/3/4 全部过 mem_guard。两条 rviz:=false 路径 10-27 白天均已 headless 验证过。
3. **`~/ugv_start_mapping.sh` 加固**：启动前打印可用内存，<500MB 强提醒，检测到 Chrome
   在跑提示关闭（不拦截）。

**遗留**：下次实车跑重栈时观察 earlyoom 是否按预期先 SIGTERM（syslog 有记录）；
若 540MB 阈值对"导航栈+桌面"太紧/太松再调 -m。

### 踩坑记录（本轮）

- `set -u` 下 source ROS 的 setup.bash 会触发 unbound variable 直接退出，且错误被 `2>/dev/null` 吞掉——
  source 必须放在 `set -u` 之前。
- pkill -f 模式会匹配**调用方整条命令行**：在测试命令里写到 "jupyter-lab" 字样，pkill 把测试 shell
  自己杀了（exit -1）。所有 pkill/pgrep 模式已用括号技巧（`jupyter-la[b]`）加固。
- jupyter 由 systemd `ugv_jupyter.service` 托管（Restart=always），kill 进程会被拉起，须 systemctl 层处置。
- Jetson 温度区有读竞态，`cat thermal_zone*/temp` 偶发 EAGAIN，读取需容错。
- `ls /dev/ttyACM0 /dev/ttyUSB*` 在 glob 不匹配时因 ls 对部分操作数失败返回非零，[ -e ] 判断才对。

## 2026-10-23 键盘遥控"跑偏"排查与修复

**现象**：用户反映键盘遥控会跑偏。排查结论：不是启错版本（桌面图标与一键建图跑的是同一个 `ros2 run ugv_auto keyboard_teleop`，install/build 均为源码软链，全工作空间仅此一份），而是两个问题叠加：

### 问题1：残留进程抢占（本次主因，已解决）
10-23 上午的多次冒烟测试用 `timeout` 杀 docker exec，容器内 `ros2 launch` 的子进程（base_node/ugv_driver/ldlidar 等）成孤儿存活，最多时 **3 套底盘驱动 + 3 个雷达节点** 同时抢串口、同话题多发。后果：雷达超时断流、/odom 与 /imu 数据来自多个实例互相打架、底盘收到重复指令。
**处置**：全部清理，确认 0 残留。**教训：结束测试用 `pkill -INT -f 'ros2 launc[h]'`（注意括号技巧防 pkill 匹配到自身命令行），杀完用 `ps` 验证。**

### 问题2：航向保持用错了反馈源（已修复）
`keyboard_teleop.py` 直行时做航向保持，原来用 `/imu/data`（互补滤波）做反馈。实测（静止 12s）：`/imu/data` 漂 ~1°（原始陀螺 z 零偏 -0.67°/s，互补滤波偏置估计没完全压住）；而 `/odom`（base_node 纯编码器推算）漂仅 0.08°，稳定两个数量级。
**修复**：航向保持反馈改为**优先 `/odom`（编码器），IMU 仅兜底**（超时 0.5s 无数据时）；新增 `h` 键随时开关航向保持。编码器能看到电机不对称造成的真实转角，正好治跑偏；IMU 原设计是防打滑，但本机 IMU 噪声比打滑危害大。

## 根因诊断

### 死机
Jetson 只有 **3.5GiB 运行内存**（4GB 模块），建图时 Cartographer + RViz2 + Chrome + GNOME 桌面总量稳超内存。溢出后先吃 1.8G zram swap，zram 压缩吃满 CPU → 画面定格、键鼠无响应，表现为"死机"；随后内核 OOM killer 杀进程。历史日志（`~/ugv.log` 末尾的 `Killed`）即为 OOM killer 痕迹。

### 漏扫
`mapping_2d.lua` 中量程配置不当：`max_range = 3.5`（LD19 雷达有效量程 8~12m），3.5m 外障碍被直接丢弃；`missing_data_ray_length = 5` 把 5m 内无回波区域画成"已探明空闲"，抹掉远处墙线。

## 注意事项

- **激光雷达物理限制**：玻璃、黑色吸光材质、低于扫描平面的矮障碍，任何激光雷达都扫不出，需加深度相机兜底。
